Kivy>=2.3.0
# Pillow ya no es sólo para íconos/generar_iconos.py: desde Fase 3.3, es el
# fallback de core/modelo.py para medir dimensiones de imágenes rasters
# (PNG/JPG/...) cuando gi/GdkPixbuf no está disponible — el caso NORMAL en
# Android/Pydroid 3, no una excepción. Sin Pillow instalado, cualquier
# conector/equipo/slot con imagen raster asociada no puede leer/escribir
# su posición en mobile.
Pillow>=10.0.0

# Fase 3.5 (2026-09-16, ver plan_svg_pygame_nanosvg_v1.md): ruta PRIMARIA
# de rasterizado SVG en mobile — ui_kivy/svg_raster_pygame.py.
#
# CONFIRMADO en dispositivo real (Pydroid 3, pygame 2.6.1 clásico —no
# pygame-ce—, SDL_image (2, 6, 3)): pygame.image.load() carga .svg
# directamente vía SDL_image/NanoSVG, probado OK sobre 7 SVG reales del
# proyecto (fondos de equipo/plano + símbolos), sin necesitar compilar
# nada (a diferencia de rlPyCairo/pycairo más abajo). Pydroid 3 YA trae
# pygame por defecto en la mayoría de sus instalaciones — si `pip install
# pygame` fallara ahí por falta de toolchain, primero probar si ya está
# disponible sin instalar nada (`import pygame` desde la consola de
# Pydroid) antes de pelear con el compilador.
#
# Limitación conocida (confirmada por los mantenedores de pygame, no
# probada todavía contra fragmentos reales del catálogo — ver
# PROGRESS.md): el motor NanoSVG no soporta <text> y está sin
# mantenimiento activo; gradientes complejos pueden fallar. Cuando esto
# pasa, ui_kivy/widgets_base.py cae automáticamente al fallback
# svglib+reportlab+rlPyCairo de abajo — no rompe la pantalla.
pygame>=2.0.0

# Fase 3.3/3.4: FALLBACK de SVG sin gi/Rsvg, para cuando pygame no está
# disponible o falla puntualmente con un SVG que NanoSVG no soporta.
#
# OJO — distinción importante entre dos cosas que este comentario tenía
# mezcladas antes (2026-09-16, investigando por qué el fondo/los símbolos
# SVG no se veían en mobile real):
#
#   (a) MEDIR el tamaño de un SVG (ancho/alto en px) — esto sí se resuelve
#       con regex puro la mayoría de las veces (SVGs con width/height o
#       viewBox explícitos, el caso típico de un export de herramienta
#       vectorial), sin ninguna dependencia adicional. Ver
#       Modelo._dimensiones_svg_sin_gi/_svg_ancho_alto_atributos/
#       _svg_viewbox_size en core/modelo.py. Sólo el caso raro (SVG sin
#       viewBox ni width/height, p.ej. sólo width="100%") necesita
#       svglib+reportlab para esto.
#
#   (b) DIBUJAR el SVG (rasterizarlo a una textura que Kivy pueda pintar)
#       — esto es SIEMPRE necesario en mobile, porque kivy.core.image.Image
#       no soporta SVG en absoluto (a diferencia de GdkPixbuf en GTK). Acá
#       NO hay atajo de regex: ui_kivy/widgets_base.py.crear_textura_imagen_svg
#       (fondo de equipo/frame) y .crear_textura_simbolo (símbolo de
#       conector) pasan primero por pygame (Fase 3.5, ver más abajo) y, si
#       eso no está disponible o falla, por svglib+reportlab como
#       fallback. Sin NINGUNA de las dos rutas instalada, CUALQUIER imagen
#       de fondo .svg (no sólo el caso raro de arriba) se muestra como
#       "Sin imagen asignada" — este es el bug reportado, no el caso raro
#       de (a). Por eso dejarlas comentadas como "opcionales" era
#       incorrecto: al menos una de las dos rutas es obligatoria para (b).
#
#   (c) HALLAZGO NUEVO (2026-09-16, probado en sandbox de escritorio):
#       svglib+reportlab NO alcanzan solas. reportlab 4.x ya no trae un
#       backend de rasterización propio (el viejo `_rl_renderPM`, C
#       precompilado sin cairo, fue discontinuado) — `renderPM.drawToFile`
#       ahora requiere el paquete `rlPyCairo`, que a su vez instala
#       `pycairo`: una extensión C que se compila contra libcairo del
#       sistema (necesita headers de desarrollo de Cairo + un compilador
#       C funcionando, vía pkg-config). Confirmado con una prueba mínima:
#       sin rlPyCairo, renderPM.drawToFile revienta con
#       "cannot import desired renderPM backend rlPyCairo"; instalando
#       rlPyCairo (que compiló pycairo sin problema en ESTE sandbox de
#       escritorio, que sí trae libcairo-dev) el render a PNG funciona.
#
#       PENDIENTE REAL (no resuelto en esta entrega, es la prueba de 15
#       minutos que este mismo archivo pedía desde antes): confirmar en
#       Pydroid 3 sobre el dispositivo real si `pip install rlPyCairo`
#       logra compilar pycairo ahí. Android/Termux/Pydroid normalmente NO
#       trae libcairo-dev accesible a pip por defecto — es el escenario de
#       riesgo real que este comentario ya sospechaba, ahora con el
#       nombre exacto del paquete que hay que probar. Si pycairo NO
#       compila en el dispositivo, el fondo SVG seguirá sin mostrarse
#       incluso con esta entrega instalada, y hace falta evaluar una
#       alternativa que no dependa de cairo (p.ej. un rasterizador propio
#       basado sólo en Pillow para el subconjunto de SVG que exporta la
#       herramienta vectorial del proyecto) — no implementado todavía,
#       ver PROGRESS_INTEGRACION_MOBILE.md.
svglib>=1.5.0
reportlab>=4.0.0
rlPyCairo>=0.3.0
